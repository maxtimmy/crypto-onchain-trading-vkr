# Сборка первой рыночной таблицы BTCUSDT

Версия `btcusdt_1h_4h_v1`: часовые фичи, доходность на 4 часа, спот без плеча. Это технический рыночный датасет; он не заменяет эксперимент с дополнительными признаками. Модели и торговые результаты на этом этапе не рассчитываются.

## Запуск

Нужен Python 3.9 или новее; сторонние пакеты и API-ключи не требуются. Команды выполняются из корня репозитория.

```bash
python3 scripts/market_data.py download --config configs/btcusdt_pilot.json --max-pages 2
python3 scripts/market_data.py download --config configs/btcusdt_pilot.json
python3 scripts/market_data.py validate --config configs/btcusdt_pilot.json

python3 scripts/market_data.py download --config configs/btcusdt_1h_4h.json
python3 scripts/market_data.py validate --config configs/btcusdt_1h_4h.json
python3 scripts/market_data.py build --config configs/btcusdt_1h_4h.json
python3 scripts/market_data.py verify-build --config configs/btcusdt_1h_4h.json
```

Короткая конфигурация покрывает 1–2 февраля 2022 года и служит проверкой загрузки/возобновления. Для расчёта 30-дневных окон этого короткого диапазона недостаточно. Основная конфигурация задаёт полуоткрытый диапазон `[2021-12-01, 2026-01-01)` UTC, минутные цены и часовую базу. Изменение диапазона или источника требует отдельного каталога снимка; существующий снимок не перезаписывается другим набором настроек.

`--max-pages` ограничивает число сохранённых страниц, чтобы проверить возобновление. Для продолжения повторяется та же команда без ограничения. `validate` по умолчанию проверяет и данные, и хеши исходных ответов; `--skip-raw-hashes` допустим только для быстрого просмотра покрытия, не для подтверждения готовности.

## Хранение и восстановление

Основной каталог — `data/datasets/btcusdt_1h_4h_v1/`, база — `market.sqlite3`. Исходные ответы сохраняются как JSON в gzip, рядом с ними — URL, параметры запроса, время получения UTC и SHA-256. В SQLite находятся свечи, состояние загрузки, подготовленные строки, исключения и метаданные сборки. Все эти данные исключены из Git; в репозиторий попадают конфигурация, код, проверки и небольшая сводка.

Состояние продвигается только после сохранения ответа и атомарного импорта страницы. При остановке уже подтверждённые страницы используются повторно без новых запросов; несовпадение контрольной суммы останавливает продолжение. Повторные ключи не создают дополнительные свечи, а конфликт содержимого не заменяет старое значение молча. Отказы сети и ограничения API обрабатываются с ограниченным числом повторов; после окончательного отказа можно продолжить тот же снимок.

Завершённая загрузка означает, что все участки диапазона проверены, а не что у поставщика нет пропусков. Пустой участок не должен останавливать получение следующих дат. Отсутствующие и неполные свечи сохраняются в отчёте качества; цена и объём не интерполируются.

## Признаки, ответ и временные границы

В момент `t` доступны только завершённые часовые интервалы, заканчивающиеся не позже `t`. Доступность рыночного снимка к `t + 60 секунд` — сценарное допущение, а не подтверждённая историческая задержка REST.

Для каждого окна `W ∈ {24, 168, 720}` часов считаются:

- Доходность `close(t) / close(t−W) − 1`.
- Реализованная волатильность: корень из суммы квадратов часовых логарифмических доходностей.
- Суммы объёмов BTC и USDT.
- Диапазон `max(high) / min(low) − 1`.

Дополнительно сохраняются доходность, диапазон и объём последней завершённой часовой свечи. Для доходности и волатильности нужна также закрытая свеча у левой границы окна. Если необходимая свеча отсутствует либо помечена как неполная/некорректная, строка исключается с причиной.

Исполнение задаётся как `e = t + 120 секунд`. Цель до торговых расходов:

```text
label_end = e + 4 часа
y = open_1m(label_end) / open_1m(e) − 1
```

Обе минутные свечи должны существовать точно в указанные моменты и пройти проверки. Поиск ближайшей цены, заполнение из будущего и подмена времени исполнения не используются.

Обучение — 2022–2023, валидация — 2024, финальный тест — 2025. Строка относится к части по `e`; `e` и `label_end` должны находиться внутри одного полуоткрытого интервала. Ответы, пересекающие следующую часть, исключаются. Покрытие и структура финального периода проверяются технически, без оценки качества модели, распределения целевой доходности и торговых показателей.

## Проверка результата

`validate` с проверкой raw повторно разбирает сохранённые ответы и сопоставляет все поля свечей, флаги качества и карантинные строки с SQLite. Изменённая цена, исчезнувшая или лишняя строка останавливают проверку, даже если файлы raw сохранили прежние хеши. Команда открывает базу только для чтения.

`build` сначала выполняет эту проверку, затем сохраняет строки, причины исключений, перечень фичей и отпечатки исходных свечей/конфигурации/результата. `verify-build` повторно проверяет отпечатки без изменения таблиц. Идентичный сохранённый снимок и конфигурация должны дать тот же результат при повторной сборке; время запуска не входит в содержательный отпечаток.

Отчёт содержит ожидаемое и фактическое покрытие `1m`/`1h`, обнаруженные дефекты, число включённых/исключённых решений и разбивку причин по частям. Дневные ончейн-данные не присоединяются автоматически: решение об их исторической доступности описывается отдельно в [разборе источников](onchain_history.md).
