# Историческая доступность ончейн-показателей

Проверка от 19 октября 2026 года. **`TxCnt` и `AdrActCnt` остаются `BLOCKED` для основного бэктеста 2022–2025 годов.** Текущая история Coin Metrics и проверенная история Git не подтверждают, какая версия была доступна в момент решения. Из блоков Bitcoin можно воспроизвести собственный счётчик транзакций, но время получения блока историческим наблюдателем из этих данных не восстанавливается.

Это завершённая проверка двух способов снять ограничение, а не выполненная полная выгрузка ончейна. Рыночная таблица на этом этапе остаётся промежуточным результатом. Обучение и торговые результаты здесь не рассчитываются.

## Свидетельства и их границы

В [небольшом файле проверки](../experiments/0002_onchain_sources.json) сохранены точные GET-адреса и параметры, время запроса и ответа в UTC, HTTP-коды, диагностические заголовки, размеры, SHA-256 ответов и выбранные поля. Ключи доступа не использовались. Полные тела больших ответов не включены в Git; для неизменяемых ресурсов записаны адреса с SHA коммита или хешем блока. Сводка явно различает сохранённые выдержки и полные ответы.

`retrieved_at_utc` и HTTP `Date` означают получение **сейчас**. Они не доказывают первую публикацию в 2022 году. Старые даты внутри ответа также не заменяют время доступности его версии. Выводы относятся к проверенным адресам и доступной на момент проверки ветке; отсутствие снимков в ней не доказывает отсутствие любых архивов у поставщика.

## Coin Metrics: текущие значения и архив Git

Повторный запрос Community API вернул три дневные строки, 1–3 января 2022 года. Значения `TxCnt` — 188065, 194826 и 241163; ответы содержат также `AdrActCnt` и `AssetEODCompletionTime`. Это подтверждает доступность нынешней истории, но не снимает ограничение из [каталога данных](data_catalog.md). В документации [API v4](https://docs.coinmetrics.io/api/v4/) для используемого `/timeseries/asset-metrics` не подтверждён выбор исторической версии на дату решения. Время завершения расчётов нельзя подменять временем первой публикации каждой версии.

[Официальный репозиторий архивов](https://github.com/coinmetrics/data) описывает дневное обновление CSV из Community API. Проверка фактической текущей истории `csv/btc.csv` дала:

| Проверка | Наблюдение |
|---|---|
| Последний коммит файла | `f1a36afb962731c387bb03982758ab0103063da5`, дата коммита `2026-05-24T13:37:39Z` |
| Последняя страница истории файла | 60-я при `per_page=1`, по заголовку `Link` |
| Самый старый достижимый коммит | [`606d84a244c53ca53b453addfd74dee7b709b2ba`](https://github.com/coinmetrics/data/commit/606d84a244c53ca53b453addfd74dee7b709b2ba), `2026-03-26T18:44:35Z`, список родителей пуст |
| История до `2022-01-10T23:59:59Z` и до `2025-01-10T23:59:59Z` | Оба запроса API вернули HTTP 200 и `[]` |
| CSV в самом старом достижимом коммите | 6291 строка, даты наблюдений `2009-01-03…2026-03-25` |

Три выбранные строки 2022 года в этом CSV совпали с нынешним API по всем трём проверенным метрикам. Это сравнение двух ретроспективных снимков; оно не показывает, какими эти строки были в 2022 году. Доступная сейчас история Git не предоставляет требуемые версии периода 2022–2025.

Даже наличие более старых коммитов потребовало бы отдельной проверки времени публичной доступности: даты автора и коммитера задаются средствами Git ([документация](https://git-scm.com/docs/git-commit#_commit_information)). Хеш фиксирует содержание версии, но сам по себе не доказывает, когда она впервые стала доступна через поставщика или GitHub. Здесь нет обвинения в изменении дат; просто такой гарантии источник не даёт.

Данные Coin Metrics используются с атрибуцией; [лицензия архива](https://github.com/coinmetrics/data/blob/master/LICENSE) — CC BY-NC 4.0. В репозиторий проекта включены только небольшие выдержки для проверки, не полная копия CSV.

## Восстановление счётчика из блоков

Публичный [Esplora API Blockstream](https://github.com/Blockstream/esplora/blob/master/API.md#blocks) без ключа вернул по 10 блоков около высот 716000 и 878000: исторические окна декабря 2021 и января 2025 года. Метаданные содержат высоту, хеш, хеш предшественника, `timestamp`, `mediantime`, `tx_count` и корень Меркла. Для блока 716000 дополнительно проверены текущий статус основной цепочки, заголовок, двоичный блок и список идентификаторов транзакций; результаты проверок записаны в JSON.

В блоке 716000 получено 1436 уникальных txid и **1435 транзакций без coinbase**. Совпали все шесть проверенных условий: хеш заголовка, его время, корень Меркла списка txid, количество транзакций в метаданных, заголовок в начале двоичного блока и его CompactSize-счётчик. Это подтверждает расчёт одного блока; полный дневной ряд и его соответствие Coin Metrics не проверялись.

Для Bitcoin `TxCnt` в определении Coin Metrics исключает coinbase ([определение метрики](https://docs.coinmetrics.io/network-data/network-data-overview/transactions/transactions)). Поэтому простой кандидат для **собственной** метрики — число транзакций блока минус одна coinbase. Заголовок Bitcoin содержит корень Меркла транзакций, но не их количество: для проверки счётчика нужны тело блока или список транзакций. Порядок и поля описаны в [спецификации Bitcoin](https://developer.bitcoin.org/reference/block_chain.html).

Минимальный алгоритм будущей реконструкции:

1. Зафиксировать хеш вершины и непрерывную цепочку её предшественников; сохранять `(height, hash, previous_hash)` и исходные ответы с контрольными суммами. Страницы `/blocks/:height` обходить по высоте, проверяя отсутствие разрывов и повторов. Не предполагать монотонности `timestamp` по высоте.
2. Для каждого блока получить `tx_count`; независимо проверить выбранные блоки по CompactSize-счётчику в двоичном теле, числу уникальных txid и корню Меркла, совпадающему с заголовком. Проверять хеш заголовка. Полная проверка правил консенсуса требует валидирующего узла; совпадение полей публичного API её не заменяет.
3. Определить отдельную метрику `btc_tx_count_ex_coinbase_by_header_day_v1`: сумма `tx_count − 1` по блокам за полуоткрытые сутки UTC согласно времени **заголовка**. Сохранять границы высот и версию цепочки. Это воспроизводимый счётчик выбранного снимка, не автоматически тождественный дневному ряду Coin Metrics. Для доказательства полноты временного окна нужно проверить все относящиеся к нему блоки, а не ограничиться пробными страницами.
4. Не присваивать исторический `available_at` из `timestamp`, `mediantime`, текущего числа подтверждений или даты сегодняшней выгрузки. В будущей собственной записи сохранять фактические `observed_at`, хеш вершины и последующие реорганизации; применять выбранную политику подтверждений к наблюдавшейся тогда цепочке.

Подробный счётчик активных адресов требует транзакций, входов и предыдущих выходов, правил извлечения адресов и дедупликации. Одних метаданных блоков для `AdrActCnt` недостаточно. В этой проверке такая реконструкция не выполнена.

**Ограничения времени принципиальны.** Время заголовка указывает майнер; оно ограничено правилами протокола и не равно времени приёма узлом. `mediantime` — медианное время блоков, тоже не журнал получения. `in_best_chain` показывает цепочку на момент текущего ответа; прежние краткие ветвления и время их наблюдения этот запрос не воспроизводит. Даже условие «шесть подтверждений» без исторического журнала вершины не даёт точного UTC-времени, когда оно выполнилось у наблюдателя. Семантика подтверждений и полей времени приведена в [Bitcoin Core RPC](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/getblockheader/).

Реконструированный счётчик можно исследовать отдельно с явно принятой моделью задержки и реорганизаций. Например, переносить завершённые сутки на несколько дней — **сценарное предположение**, а не сертификат исторической доступности. Такой вариант требует изменения протокола эксперимента с обозначением ограничения и не допускается молча в основной бэктест с требованием подтверждённого `available_at`.

У публичного Blockstream есть ограничения частоты; актуальное [сообщение поставщика от 22 апреля 2026 года](https://blog.blockstream.com/enhanced-analytics-and-infrastructure-improvements-for-the-blockstream-explorer-api/) подтверждает лимиты бесплатного доступа, но не обещает числовую квоту для наших неавторизованных запросов. Успешная небольшая проба не гарантирует бесплатную массовую выгрузку. Загрузчик должен ограничивать частоту и останавливаться при 429 с соблюдением `Retry-After`; платные тарифы и регистрацию с оплатой не подключаем. Альтернатива — собственный узел, который требует локальных ресурсов и также не восстанавливает прежний журнал получения автоматически. Лицензия программы Esplora не используется как лицензия чужого датасета.

## Решение и следующий шаг

| Вариант | Статус для основного исторического бэктеста |
|---|---|
| Нынешние `TxCnt` / `AdrActCnt` Community API | `BLOCKED`: нет проверенных версий с историческим временем доступности |
| Проверенная текущая Git-история `csv/btc.csv` | `BLOCKED`: доступные версии начинаются в 2026 году; время первой публикации отдельно не подтверждено |
| Собственный счётчик из блоков | Воспроизводимость значения технически подтверждена на ограниченной пробе; исторический `available_at` не восстановлен. В основной бэктест не включён |

Следующий конкретный шаг для сохранения строгого протокола — **получить у Coin Metrics описание доступного архива версий за 2022–2025 годы с документированным временем их публичной доступности и бесплатными условиями учебного использования**. Запрос поставщику в этом этапе не отправлялся. При отсутствии такого архива ограничение остаётся явным; использование собственной метрики с моделируемой задержкой должно быть отдельным решением о постановке исследования.
